# Host seams

**Every place the library asks the host for something, and what disappears
when the host provides nothing.**

The library never talks to a backend, an analytics service or a search
index. It exposes a service identifier; the host registers an implementation
as an extension in the editor specs. Most seams are optional: the code reads
them with `std.getOptional(...)` and degrades. The table below says how.

All identifiers are exported from `@labre/affine/shared/services` unless
noted. Register with `di.override(Provider, () => impl)` or the ready-made
`XExtension(impl)` helper.

**Hosted database sources.** `HostedDataSourceBase(hostModel, resolveSource)` (ADR 0035 §7, B1) keeps the views in `hostModel.props.views`; each view names the source it reads by its stored `sourceId` (absent on every view stored before 0.49). `resolveSource(sourceId)` returns `{ schema, rows }`: the `affine:database` block whose `props.columns` is that source's schema, and a signal of its ordered row ids; `null` when there is no such source. The data layer (`rows$`, `schema$`, and the getters your subclass implements over `schema$`) answers for the current view's source; `sourceMissing$` says when it has none. Nothing is written while resolving. A source whose rows are documents overrides `rowsAreDocuments` (`true`), answers each title from its own store with `titleOf(rowId)` and returns `hostedTitleColumnConfig` from `propertyMetaGet('title')` (ADR 0035 §9f, B15): the title is a plain string drawn and edited by the plain-text cell, a committed title reaches your `cellValueChange` as a string, and no row's document is loaded to draw it.

**Full-page database and "+ view" (`@labre/core-database`, ADR 0035 B11, B13).** No seam of their own. A database page is the inline table moved to a page: mount `<affine-database-page .store=${store} .extensions=${pageExtensions} .hostBlockId=${id}>` (exported as `DatabasePageHost` from `./view`, defined by `DatabaseEditorViewExtension`) with the database document's store and the page extensions you would give its page editor (its `DatabaseDataSourceProvider` answering a `HostedDataSourceBase` for the views' block); `element.std` is the editor it builds. Keep `<doc-title>` above it, since the page title is the database's name, and set its `bodyBlockId` to the same id: Enter and ArrowDown then leave the title for the database (the first cell of a table or kanban view) and never add a paragraph to the note; without it the title keeps the page behaviour of 0.48 and writes into a note this page never draws. It draws the views' block alone, without its title row and without the page root's chrome or handlers; the schema blocks and the note are never drawn, never selectable (the guard owns the store's selection: mount no other editor on that store meanwhile) and a file drop never reaches them; nothing inserts into the note and nothing is written; without a block of that id it says "This database has no views to show." (`com.labre.database.page.host-missing`). The view bar is core's: as many tabs as the width allows, the rest under "N more" (`com.labre.data-view.views-bar.more`, `{{count}}`), the current view always a tab, 44px targets on a phone. With `DatabaseEditorToolingViewExtension` registered, its "+" on a source that resolves sources offers "On an existing source" (each source the views read, by its schema block's title, plus, with your `DataSourcePickerExtension`, the sources of the block's database, its `externalSourceId`, that no view reads yet) and, when your picker has `createSource`, "With a new source" (it calls `createSource(externalSourceId)`, then adds a table on the new source); a new view stores the `sourceId` of the source it was added on. Without the bundle, or on an inline database, "+" lists the creatable presets.

**Cell hydration.** When values arrive after rows (ADR 0035 §9e, B2), answer `cellStatus(rowId, propertyId)` with `pending` until the value is the real one (`error` if it failed), and `valuesState$` with `{ status: 'loading' | 'ready' | 'error', since: Date.now() }` for the whole source; offer `retryValues()` if you can try again. A pending cell draws a skeleton, a failed one stays empty; neither mounts its editor nor accepts a write (a paste, a fill or a kanban drop on it does nothing). Group counts and column statistics show "…" until `ready`; after 3 s of `loading` a banner says values are still loading (`com.labre.database.values.loading`), and on `error` a banner says they could not be loaded (`com.labre.database.values.error`) with Retry (`com.labre.resource.status.retry`) when `retryValues` exists. The library writes nothing in any state.

**Fonts.** `CommunityCanvasTextFonts` is a sane default but points at `fonts.cdnfonts.com`: a host that promises no third-party request self-serves the files and passes the same list with its own `url`s. A family with no face in the registered list is not offered by the text font-family picker; a text already stored in it keeps it, paints the `sans-serif` fallback and shows the family name greyed as unavailable, and nothing is rewritten. Neither default list carries Satoshi since #396 (its licence forbids offering it as a selectable font in a SaaS); Plus Jakarta Sans (SIL OFL 1.1) replaces it.

**Title band.** `sheet$(docId)` returns a signal synchronously (`loading`, `ready`, `missing`, `error`, as for pivot properties); `ready` holds the page's **visible** properties in the order to draw them, `{ id, namespace, name, type, data, value, readonly }`, where `type` and `data` are a data-view property type and its config and `value` the JSON a data-view cell of that type holds. You resolve visibility; a visible property with no value comes back with `value: null` and draws an empty chip that can still be clicked. Each value is drawn and edited by the cell the inline table mounts for its type, with the table's look (ADR 0035 §11, amended 2026-10-13): the checkbox toggles, `select` and `multi-select` open the table's tag menu (on your options only, unless the property may change them: see below), `date` opens the table's date picker, `number`, `progress` and the text types (`text`, `rich-text`, `title`, `email`, `phone`) the table's inputs; `link` and `url` are drawn by the database block's link cell when its view extension is registered, by the text cell otherwise; `created-time` and `modified-time` are drawn read-only by the date cell. A number reads as in a table cell: unformatted unless `FeatureFlagService` turns `enable_database_number_formatting` on. Any other type keeps a plain-text reading that opens your properties panel, or nothing. A value the cell commits calls `set(docId, propertyId, value)` (`null` for an emptied one, nothing for an unchanged one): the chip shows pending until the promise settles, and the new value must come back through `sheet$`, since the band never applies it. A rejection is yours to report and roll back. The band is drawn by `<doc-title>` under the title and by the page note's head on the canvas, inside the note, so it follows the zoom; on the canvas it is interactive while the note is being edited, like the rest of the note. `notShown$(docId)`, optional, is the list of child pages this document holds but does not display (labre ADR-0045 §7); the band draws it in both views as a "Not shown on this page" row. A page's title opens it through `RefNodeSlotsProvider.docLinkClicked`; its "Show here" (`com.labre.title-band.show-here`, writable documents only) inserts an `affine:embed-linked-doc` card of it, at the end of the last note in the page view and at the centre of the visible canvas on the canvas, as one undo step. The library writes only that card: you compute the list, and you drop the page from it once your reading of the document finds the card. Do not draw a row of your own under the title: the band already does.

**Title band options.** A `select` or `multi-select` chip creates and renames options only when your service has `setData(docId, propertyId, data)` and the property comes with `dataWritable: true`, on a chip that is not `readonly`. Then the tag menu offers "Create" and a rename field per option (no delete, no colour, no reorder: those stay in your properties panel). Each change calls `setData` with the whole config, `{ ...data, options }`, options in `{ id, value, color }` with a created option first; a creation is followed by a `set` that selects it, so apply the two in order. The band never applies `data`: the new options come back through `sheet$`. A rename sends one call per keystroke, as the table does; coalesce if you need to. A rejection is logged. Do not mark `dataWritable` a select whose option ids are its labels (the Labre app's `tags`): a rename would change its values.

**Database rows and sources.** `DatabaseOpenRowExtension` is the one path every view takes to open a row (`DataViewRootUILogic.openDetailPanel`); a host that routes rows to its own pages reads `mode` and `newTab` and does the navigation. `DataSourcePickerExtension.list()` returns a signal of `{ id, title, sources: [{ id, title }] }`, where `id` is the `externalSourceId` the inserted block will carry (opaque to the library); the picker reads it as it draws, so a list filled late shows up. `importView(request)` receives the database the copy lands in (`databaseId`), the current view's `sourceId`, that source's `properties` and the `layouts` it adds: let the reader choose a view (any database it may read, or a template you kept), map each of its properties to one of `properties` or ignore it, then call `request.add({ view, properties, mapping })`; the library copies it as a new view on that source (one undo step), removing the filters and sorts on ignored properties, and returns its id or `null` (the page turned read-only, a layout not offered). `remapView` (`@labre/core-database`) gives the same copy and its counts beforehand, for your dialog to say what is removed. `saveViewTemplate(template)` receives the current view without its filters, sorts and manual orders, with its source's properties; keep it where you keep templates and offer it back through `importView`. The full page of a database registers its "This view" entries as `'view-menu'` commands (`database.view.layout`, `.group`, `.open-in`, `.properties`, `.save-template`, `.import`): list them with `getViewActions(std, 'page')` on the page's `std` and run them with `runViewAction`; a setting opens the view settings' own menu on the view's options button. A picked source is inserted as an `affine:database` block with that `externalSourceId`, the database title and one view with that `sourceId`, as one undo step; a board on a source with nothing to group by lands as a table. `popDataSourcePicker` (`@labre/core-database/view`, with `databaseId` for one database's sources) is the picker a "+ view" opens. `DatabaseNewRowMenuExtension.open` receives the chevron as `anchor` to hang your menu from, the `affine:database` block and the view; the library draws nothing of the menu and adds no row for it: a template you apply is your own write. A hosted source that offers a text column lists `hostedTextColumnConfig` (`@labre/affine/blocks/database`, type `text`, a plain string value) in `getPropertyMetas` and returns it from `propertyMetaGet('text')`: data-view's own plain-text preset is hidden from the menus, because the inline database's Text is `rich-text`.

**Saved frames.** `FrameTemplateProvider` changes no stored format. "Save as template" on the toolbar of ONE selected frame calls `save({ docId, frameId, title, snapshot })`: `snapshot` is a `DocSnapshot` of the frame, its descendants (groups opened, nested frames included) and the notes it holds, serialized by the surface transformer, so every stored key of every element crosses unchanged except `layer` (dropped: the copy lands in the inserting viewer's active layer, ADR 0031 §6) and a connector end outside the frame (turned into a free position, as a paste does). Images and attachments are referenced by their blob id, never copied. The library shows the outcome (`com.labre.frame.toast.template-saved`, or `com.labre.frame.toast.template-save-failed` on a rejection) through `NotificationProvider`, or its own toast: do not notify yourself. A read-only viewer may save too, since nothing is written to the document; refuse in `save` if you must. `list()` returns `{ id, title, snapshot, preview? }` and is called only when the Templates panel shows the "Saved frames" tab (`com.labre.template.panel.category.saved-frames`, last tab, identity `SAVED_FRAMES_CATEGORY`) or searches across tabs, never at mount; a tile is inserted by the canvas template job like any template (fresh ids, the frame's children remapped, active layer). `frameDeleted({ docId, frameId })` is called for a frame THIS viewer deleted on a writable document, never for a deletion another peer made, and for every frame (ignore ids you do not know); `frameRestored` is called when this viewer brings back, in the same session, a frame it had deleted (undo). Whatever `frameDeleted` does must be undone by `frameRestored`: move to the trash, never destroy. Make both idempotent: two editors on one document report the same gesture twice. `frameInserted({ docId, templateId })` is called once a tile of the "Saved frames" tab is on the canvas (after the template job resolved, never for a failed insertion), with the document it landed in and your `id` for the template: link what the copy references (its images) to that document, or a guest of that page will not see them. Absent, nothing is called. A host category of its own goes through `TemplateCategoryExtension(category)` (`@labre/affine/gfx/template`), per editor; the module-level `EdgelessTemplatePanel.templates.extend(...)` is gone.

**Exports of a view.** No seam: the editor never asks you for an export, you list and run them. `getViewExports(std, mode?)` (`@labre/affine/host-panels`) returns the view actions of section `'export'` for the view you show: `page.export.markdown` and `page.export.html` in both views, and on the canvas `canvas.export.png`, `.pdf` (with an `ExportManager`), `.drawio`, `.svg` (whole canvas) and one `canvas.export.<framework>.<format>` per `*:export` capability a framework registered (so its flag decides), listed while the board holds that framework's elements. `runViewAction(std, id)` resolves with `{ file }` (a `Blob` and a sanitised name) and downloads nothing; the same commands run from the palette download. Ids, labels, `labelParams` and icon keys: [08-host-panels.md](08-host-panels.md#exports-of-a-view).

**Pasting in a page.** No seam of its own: what a paste offers follows from seams already in this table. Plain text that is ONE http(s) URL and nothing else (`lonePastedUrl`, `@labre/affine-inline-link`) still pastes as a plain link, then the link's own toolbar opens on it, as on a hover, so its view switcher offers "Card view" and "Embed view" beside "Inline view" (labre REQ-IM-1). Nothing is converted unless the reader picks one; the next key or a press outside the toolbar closes it and the link stays. "Card view" is offered when the bookmark view (or the card of an embed provider matching the URL) is registered, "Embed view" when an embed provider or an `EmbedIframeConfigExtension` matches the URL and its view is registered; the embed is the sandboxed iframe of that registry. The proposal asks nothing of the network: only a view the reader picks may, through the link-preview service, whose default endpoint is in the table. A URL your `ParseDocUrlExtension` recognises becomes a reference to that document, not a link, and opens nothing. A sentence holding a URL, a `mailto:` and a refused scheme paste as text. Pasted text that holds a GFM table becomes an inline table (`affine:table`), never a database, whether it is pasted or imported as Markdown: every cell keeps its text, escapes resolved, extra cells kept as columns, an image as a link named by its alt text (REQ-IM-2). On the canvas a paste outside a note is unchanged (a URL lands as a card); a paste inside a note being edited takes the page path above.

**Theme.** The theme is a host seam with two halves.

- _Which scheme is in force._ `ThemeService` (`packages/affine/shared/src/services/theme-service.ts`) asks the `ThemeExtensionIdentifier` registration for two signals: `getAppTheme()` for the page editor and `getEdgelessTheme(docId)` for the canvas. Each is optional; a missing one is replaced by an observer on `document.documentElement.dataset.theme`.
- _What the colours are._ The library reads `@toeverything/theme` two ways: as CSS variables by their `--affine-*` names (in styles, through `cssVar` / `cssVarV2`), and as JS tables of values where a `var(…)` cannot go. Canvas painters resolve a variable through `ThemeService.getCssVariableColor`, which looks it up in `combinedLightCssVariables` / `combinedDarkCssVariables` (the chrome accent on the canvas, `getChromeAccentColor`, goes that way); the toolbars (`packages/affine/components/src/toolbar/styles.ts`) bake values from the same tables into their own selectors; the model builds the canvas palette from `lightThemeV2` / `darkThemeV2`.

So **a CSS-only override of an `--affine-*` variable does not re-skin the editor**: it repaints the DOM that reads the variable, but not the canvas painters, the toolbars or the canvas palette, which read the package's JS values. To substitute the theme, override the package itself in your package manager with a copy of your own, e.g. `pnpm.overrides["@toeverything/theme"] = "link:./packages/theme"` (the Labre app does this). The substitute keeps every `--affine-*` variable name and exports every name the library imports, listed in [01-install.md § Styles](01-install.md#styles) and frozen by `theme-imports.unit.spec.ts` (`packages/affine/all`). Mind the canvas palette: a colour picked from it is stored on the element as a value, so changing `edgeless/palette/*` or `edgeless/note/*` changes what new elements write into documents (DESIGN.md, The Untouched Data Rule).

## How to read this table when something is missing

If a button "never existed", check the seam before filing a bug. The Labre
application documents each of its registrations in
`apps/web/src/modules/editor/extensions.ts` with the reason; copy that habit.

## How to add a seam (library side)

1. Define the identifier and the extension helper next to the service.
2. Read it with `std.getOptional(...)` and decide the degraded behaviour
   explicitly (hide the button, log once, fall back).
3. Add a row to this table.
4. Give it a test that mounts without the provider.
